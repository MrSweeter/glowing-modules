# Glowing Modules

_The history of every Odoo module._

**See which Odoo modules were added, removed or moved between any two Odoo versions**, from 5.0 to `master`,
across `odoo/odoo` (Community), `odoo/enterprise`, `odoo/design-themes` and `odoo/industry`.

**→ <https://mrsweeter.github.io/glowing-modules/>**

Built for developers, functional consultants and upgrade teams who need to answer "what changed between
version X and Y, and in which repository?".

## Features

- **Compare any two versions** (all major, `saas-*` and `master` versions). The default is the latest major
  release against the previous one. Every intermediate change is taken into account, so a module added and
  removed again inside the range is not reported.
- **Moved modules** (same name, different repository, e.g. Community → Enterprise) are listed first, above the
  added and removed ones.
- **Search** with regular expressions (syntax behind the ⓘ button, see below). Matches are highlighted, and the
  version picker shows how many matching modules changed in each version.
- **Filter panel** (Filter button in the search bar): owner and repository filters, and module-name chips (Tests,
  Localization `^l10n_`, Website, Point of Sale, …) that cycle show only → hide → off. They only write `name:` /
  `-name:` terms in the search bar. Shows a count of active
  filters and has a reset button.
- **Your repositories** (Settings panel, gear button in the header): add a public GitHub repository that uses Odoo version branches (`17.0`,
  `saas-17.2`, `master`), for example `OCA/sale-workflow`. Its modules join the comparison, search and details like
  the Odoo repositories. Modules are the top-level folders with a `__manifest__.py`; other branches are ignored.
  Repositories of the `odoo` organisation and their forks are refused (already included). The list and a copy of
  the data are saved in the browser and can be removed. GitHub is only called when you click Add or Refresh,
  never automatically; a copy older than a week is flagged as outdated. Up to 5 repositories; GitHub
  allows about 60 anonymous requests per hour, roughly 2 plus one per version branch for each repository.
- **Module details:** availability ranges, a timeline, the full history and a link to the source on GitHub.
- **Shareable links:** the URL keeps the versions, search and filters; copy it from the address bar.
- Light and dark theme: follows the system by default, with a Theme selector in the Settings panel. Keyboard accessible,
  works on mobile.

### Search syntax

| Query | Meaning |
|---|---|
| `account` | module names containing "account" (case-insensitive, 3+ characters) |
| `^l10n_(be\|lu)_` | regular expressions work |
| `account edi` | several words must all match |
| `repository:enterprise` (or `repo:`) | only that repository; several `repository:` terms are combined with OR |
| `owner:odoo` | only repositories of that owner |
| `name:^pos_` | only module names matching; several `name:` terms are combined with OR |
| `-name:^l10n_` | hide module names matching |

### URL parameters

`?from=17.0&to=18.0&q=account+repository:enterprise&m=hr_payroll`. Every parameter is
optional; defaults are left out of the URL.

## Data

- The live data is a JSON file in a [gist](https://gist.github.com/GaetanVandenBergh/35a02a7148d9919a9aea76796d824d63),
  generated by a private checker and based on
  [mao-odoo/all_standard_odoo_apps_per_version](https://github.com/mao-odoo/all_standard_odoo_apps_per_version).
- A copy is committed in `public/data/glowing-modules-diff.json`. It is used for local development, for tests,
  and by the site as a fallback when the gist is unreachable. A weekly workflow opens a PR when it changes.
- Format: see [docs/data-format.md](docs/data-format.md).
- Wrong data? [Report a data issue](https://github.com/MrSweeter/glowing-modules/issues/new?template=data_issue.yml).

## Development

Requirements: Node.js 24 (see `.nvmrc`) and npm.

```sh
npm ci
npm run dev                          # http://localhost:5173/glowing-modules/ with the local data copy
VITE_DATA_SOURCE=remote npm run dev  # same, with the live gist
npm run data:pull                    # refresh public/data/glowing-modules-diff.json from the gist
npm run preview                      # production build served at http://localhost:4173/glowing-modules/
```

In dev only, `?data=local`, `?data=remote` or `?data=/path/to/file.json` in the page URL overrides the data source.
Fixtures for edge cases live in `tests/fixtures/` (e.g. `?data=/glowing-modules/…` after copying one to `public/`).

| Command | What it does |
|---|---|
| `npm run lint` | Biome (JS, JSON, HTML) + Stylelint (SCSS) |
| `npm run format` | Auto-format everything |
| `npm test` | Unit tests (Vitest); `npm run test:coverage` for coverage |
| `npm run test:e2e` | End-to-end and accessibility tests (Playwright + axe) on the production build. Run `npx playwright install chromium` once. WebKit is opt-in: `PW_WEBKIT=1` (after `npx playwright install webkit`). |
| `npm run icons:fetch` | Regenerate the Material Symbols subset after adding an icon to `scripts/fetch-icons.mjs` |
| `npm run assets:build` | Regenerate the logo, icons and social image from `design/` |

### Project structure

```
index.html              page shell (static content, dialogs)
src/main.js             bootstrap: data loading, store, events, URL sync
src/domain/             pure logic: versions, snapshots & comparison, history, search, links
src/data/               data source resolution, fetch with timeout/retry/fallback, validation
src/state/              store, version selection rules, URL ⇄ state, view model
src/ui/                 rendering (DOM built with text nodes only, never innerHTML)
src/styles/             custom SCSS (BEM `gm-*`, tokens as CSS custom properties, light/dark)
public/                 static files copied as-is (icons, data snapshot, robots, 404…)
scripts/                data pull, icon subset, asset generation, data summary
tests/unit, tests/e2e   Vitest and Playwright suites
design/                 source artwork
```

See [docs/architecture.md](docs/architecture.md) for the runtime layers, the data flow and what each tool is for.

## Deployment

Pushing to `master` runs the checks and deploys **only the production build** (`dist/`) to GitHub Pages
(`.github/workflows/deploy.yml`). A daily workflow checks that the site and the data source are up.
The site uses a Content-Security-Policy (meta tag), self-hosts every asset, and has no third-party request
apart from the data gist, and the GitHub API when a visitor adds one of their repositories.
